# 파일 탐색 기준

목표는 필요한 파일만 읽어서 토큰과 시간을 아끼는 것이다.

## 시작할 때 읽는 순서

새 세션은 이 3개만 읽고 시작한다.

1. `CLAUDE.md`: 저장소 지도.
2. 오늘 `ai.md`에서 내 블록 부분만.
3. 오늘 `progress.md`의 마지막 항목만.

- 이유: 진입점을 고정하면 시작할 때마다 전체를 훑지 않는다. 어기면: 코드 한 줄 쓰기 전에 문맥이 찬다.
- 그다음부터는 검색으로 찾은 파일만 연다. 저장소 전체 목록을 다시 뽑지 않는다.

## 읽기 제한

- 파일을 열기 전에 Grep이나 Glob으로 찾는다.
  - 이유: 찾는 한 줄 때문에 파일 전체를 읽을 필요가 없다. 어기면: 긴 파일 통독이 호출마다 비용으로 붙는다.
- 200줄이 넘는 파일은 offset과 limit로 필요한 부분만 읽는다. 전체가 꼭 필요하면 이유를 진행 기록에 적는다.
  - 이유: 큰 파일 한 번이 작은 파일 수십 개 값이다. 어기면: 블록 토큰 예상을 금방 넘긴다.
- 바뀌지 않은 파일을 다시 읽지 않는다. 내가 방금 고친 파일을 확인하려고 다시 읽지도 않는다.
  - 이유: 내용이 이미 문맥에 있다. 어기면: 같은 내용을 두 번 비용 낸다.
- 읽지 않는다: `node_modules/`, `.next/`, `dist/`, `build/`, `coverage/`, 잠금 파일(`package-lock.json`, `pnpm-lock.yaml`), `.env`.
  - 이유: 생성물은 판단에 쓸모가 없고, `.env`에는 키가 있다. 어기면: 한 번에 수만 토큰을 쓰거나 키가 기록에 남는다.
- 명령 출력은 전체를 받지 않는다. 실패 줄과 앞뒤 몇 줄, 마지막 요약만 본다.
  - 이유: 시험·빌드 로그가 가장 큰 낭비다. 어기면: 로그가 문맥을 채운다.

## 하위 에이전트에 맡길 때

- 파일 5개 이상을 훑는 탐색, 긴 로그 읽기는 Sonnet 하위 에이전트에 맡기고 결론과 `파일:줄`만 받는다.
  - 이유: 원문이 메인 문맥에 들어오지 않는다. 어기면: Opus 문맥이 탐색 결과로 찬다.
- 대상을 아는 조회와 파일 4개 이하는 직접 한다.
  - 이유: 위임에도 비용이 든다. 어기면: 간단한 조회에 에이전트 비용이 붙는다.
- 맡긴 조사를 직접 다시 하지 않는다.
  - 이유: 같은 비용을 두 번 쓴다. 어기면: 위임 효과가 사라진다.

## 지도 유지

- 최상위 폴더를 만들거나 옮기면 같은 PR에서 `CLAUDE.md` 지도를 고친다.
  - 이유: 지도가 틀리면 전체 탐색으로 돌아간다. 어기면: 다음 세션이 없는 경로를 찾는다.
- 계획 파일은 `docs/plans/YYYY-MM-DD-<이름>/`에 둔다. 다른 위치에 만들지 않는다.
  - 이유: 찾을 곳을 한 곳으로 줄인다. 어기면: 옛 계획을 최신으로 착각한다.
