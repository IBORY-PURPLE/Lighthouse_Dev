# PR, Codex 검증, 병합, 배포

Claude가 구현하고, Codex가 기능을 QA로 검증한다. Codex 검증은 필수다.

## 브랜치와 푸시

- 브랜치는 데모 단계 번호만 이름에 넣어 두 층으로 만든다. 단계 브랜치 `stage/demo<N>`은 최신 main에서 따고, 기능 브랜치 `feat/demo<N>/<기능영문>`은 그 단계 브랜치에서 따서 작업한다. `git push github <브랜치>`로 올린다. 푸시 대상을 항상 적는다.
  - 예: `stage/demo4` 아래에 `feat/demo4/upload`, `feat/demo4/resize`. 단계 이름은 쓰지 않는다. `demo`는 소문자로 쓴다(Windows는 대소문자를 구분하지 않아 `Demo4`와 `demo4`가 충돌할 수 있다).
  - 이유: 이름만 보고 어느 단계의 어느 기능인지 안다. 어기면: 브랜치가 늘수록 무엇의 것인지 헷갈린다.
- 기능 브랜치 이름을 `stage/…/<기능>`으로 짓지 않는다. `feat/`로 시작한다.
  - 이유: git은 `stage/demo4`가 있으면 `stage/demo4/upload`를 만들 수 없다(같은 경로가 파일이자 폴더가 되기 때문. 이 PC에서 직접 시험하지는 않았다). 어기면: 브랜치 생성이 거부된다.
- 문서 브랜치는 `docs/demo<N>/<이름>`(특정 단계 문서) 또는 `docs/<이름>`(단계 무관)이다. 단계 번호는 이용자가 정한 데모 시나리오의 단계다.
  - 이유: 같은 단계의 문서와 코드를 이름으로 묶는다. 어기면: 날마다 다른 이름이 생긴다.
- 병합이 끝난 브랜치는 지운다. 저장소 설정의 "병합 후 브랜치 자동 삭제"를 켠다(`stage/*`도 병합되면 지워진다).
  - 이유: 남은 브랜치가 헷갈림의 가장 큰 원인이었다(2026-11-09 이용자 결정). 어기면: 끝난 브랜치가 쌓인다.
- 기능 브랜치는 서로에게서 따지 않고 항상 단계 브랜치의 현재 끝에서 딴다. 앞 기능 PR이 단계 브랜치에 병합된 뒤 다음 기능을 시작한다. 앞 기능이 보류라 병합되지 않았는데 뒤 기능이 의존하면 아래 "보류 PR 위에 쌓기"를 따른다.
  - 이유: 병합된(squash) 브랜치 위에서 딴 브랜치는 충돌한다(11/5 #9, #12). 어기면: 병합마다 충돌을 푼다.
- 기능 PR의 base는 `stage/demo<N>`이고, 단계 PR(`stage/demo<N>` → main)은 그 단계의 기능이 모두 끝났을 때 하나 연다.
  - 이유: main에는 검증된 단계만 들어간다. 어기면: 반쯤 된 단계가 main에 들어간다.
- main 직접 커밋·푸시, 강제 푸시, `origin` 푸시는 하지 않는다.
  - 이유: main은 검증을 거친 코드만 받는다. 어기면: 검증 없는 코드가 기준이 된다.
- 커밋에 `.env`와 생성물을 넣지 않는다. 커밋 전에 `git status --short`를 본다.
  - 이유: 비공개 저장소여도 키가 기록에 남으면 지우기 어렵다. 어기면: 키를 교체해야 한다.

## PR 본문

아래 항목을 모두 채운다.

1. 기능과 합격 기준(그날 `ai.md` 블록)
2. 검사·시험 명령과 결과 요약
3. 스크린샷 링크(화면 변경 시)
4. Codex 판정과 심각한 지적 수
5. 실패 횟수와 실패 목록(`success-criteria.md`)
6. 사람 판정 대기 항목
7. 판정: `AI 병합` 또는 `보류`와 이유

- 이유: 아침에 PR만 보고 판단할 수 있어야 한다. 어기면: 판단하려고 대화 기록을 뒤진다.

## 화면 증거

- 스크린샷은 `evidence` 전용 브랜치의 `<PR번호>/` 아래에 올리고 PR 본문에서 링크한다. 기능 브랜치와 main에는 넣지 않는다.
  - 이유: GitHub CLI는 PR에 이미지를 올리지 못하고, 이미지가 main에 쌓이면 탐색이 지저분해진다. 어기면: 저장소가 무거워진다.
- PR당 핵심 화면만 올린다. 화면 하나당 1장이 기준이다.
  - 이유: 아침 검토 시간은 짧다. 어기면: 볼 수 없는 분량이 쌓인다.

## Codex 검증

- 기능 PR을 열 때마다 1회 돌린다. 기능이 합격 기준대로 작동하는지 QA로 확인하게 한다.
- 시험은 Claude가 PR의 최종 커밋에서 돌려 전체 출력을 `test-results/<PR번호>-<명령>.txt`에 저장한다. 첫 줄에 커밋 해시와 명령, 끝에 종료 코드를 적는다. Codex는 시험을 돌리지 않고 이 기록과 코드를 읽어 판정한다.
  - 이유: Windows에서 `codex exec -s workspace-write` 안의 Vitest·Playwright가 `spawn EPERM`으로 시작하지 못한다(2026-11-05 확인, 이용자 결정). 어기면: 코드 결함 없이 모든 PR이 Codex 실패로 보류된다.
- 샌드박스를 넓히지 않는다(`danger-full-access` 금지).
  - 이유: 안전 훅은 Codex에 적용되지 않는다. 어기면: 잠든 사이 Codex가 저장소 밖까지 제한 없이 접근한다.

```bash
codex exec -s workspace-write -o <결과 파일> "<PR 번호, 합격 기준, 기록 파일 경로, 시험 실행 금지 지시>"
```

- 프롬프트에는 합격 기준과 기록 파일 경로만 넣고, Claude의 결론은 넣지 않는다. Codex는 코드를 고치거나 커밋하지 않는다.
  - 이유: 독립 검증이어야 한다. 어기면: 만든 쪽의 판단을 되풀이한다.
- 기록의 커밋 해시가 현재 HEAD와 다르거나 기록이 없는 항목은 판정 불가이며 `미완료`다. PR 본문에 `Codex: 시험 기록 판정(직접 실행 아님)`이라고 적는다.
  - 이유: 시험 실행은 독립 검증이 아니다. 어기면: 사람이 Codex가 직접 시험했다고 오해한다.
- 판정: 기능 오작동, 합격 기준 미달, 보안 문제가 0건이면 `통과`. 사소한 지적은 PR에 남기고 넘어간다.
  - 이유: 사소한 지적까지 고치면 8시 안에 끝나지 않는다. 어기면: 밤이 다듬기에 쓰인다.
- 결과는 PR 댓글로 남긴다. 심각한 지적은 고친 뒤 다시 돌리되, 같은 실패 3회면 멈춘다.
- Codex를 돌리지 못하면(로그인, 한도) `미완료`로 둔다. 건너뛰고 완료로 쓰지 않는다.
  - 이유: 완료 조건은 Codex 통과다. 어기면: 검증 없는 PR이 완료로 보인다.

## 코드 리뷰 도구

- Cursor Bugbot은 PR 검증에서 쓰지 않는다. 결과를 기다리지 않고 체크 목록에도 넣지 않는다.
  - 이유: 결과가 느려 밤 시간을 잡아먹는다(이용자 결정, 2026-11-05). 어기면: 대기만 하느라 블록 시간이 샌다.

## 병합

| PR 상태 | 처리 |
|---|---|
| 기능 PR(base `stage/…`): 실패 횟수 0, Codex 첫 판정 통과, 보류 기능 위에 쌓이지 않음 | AI가 `gh pr merge --squash`로 단계 브랜치에 병합 |
| 기능 PR: 실패 이력 있음, Codex를 한 번이라도 통과 못함 | `hold-morning` 라벨, 사람이 아침에 확인 후 병합 |
| 보류 기능 PR 위에 쌓인 PR | `hold-morning` 라벨, 사람이 확인 |
| 단계 PR(base main): 안의 기능 PR이 모두 AI 병합이었고 단계 전체 시험이 통과 | AI가 `gh pr merge --squash`로 병합 |
| 단계 PR: 안에 보류 기능이 한 번이라도 있었음, 또는 단계 전체 시험 실패 | `hold-morning` 라벨, 사람이 아침에 확인 후 병합 |

- 이유: 한 번이라도 실패한 기능은 사람이 본다(이용자 결정). 어기면: 흔들린 코드가 확인 없이 main에 들어간다.
- 아침 점검 뒤 AI 병합: `hold-morning` PR도 이용자와 함께 점검해 OK를 받으면 AI가 `hold-morning`을 빼고 `reviewed-ok`를 붙인 뒤 `--squash`로 병합한다(2026-11-10 이용자 결정). 훅(`guard.js`)은 `reviewed-ok`가 있을 때만 이 병합을 허용한다. 라벨은 이용자가 OK한 PR에만 붙이고 PR 댓글에 근거(점검 내용, 예외 승인)를 남긴다. 라벨 붙이기와 병합은 명령을 나눠 실행한다(훅이 실행 전에 라벨을 본다). 병합 후 브랜치는 자동 삭제된다.
  - 이유: 아침마다 사람이 병합 버튼을 누르는 수고를 없애되 점검은 남긴다. 어기면: 점검 없이 라벨만 붙어 흔들린 코드가 들어간다.
- 개발 중 실패도 세므로 많은 PR이 보류될 수 있다. 정상이다. 병합하려고 실패를 숨기지 않는다.

## 보류 PR 위에 쌓기

- 뒤 기능이 보류 PR에 의존하면 그 브랜치에서 이어서 만들고, PR의 base를 보류 브랜치로 둔다.
  - 이유: 밤을 멈추지 않으면서 아침 결정을 존중한다. 어기면: 뒤 블록이 비거나 보류 코드가 main에 들어간다.
- 의존하지 않으면 단계 브랜치의 현재 끝에서 시작한다(단계 브랜치가 아직 없으면 최신 main에서 단계 브랜치부터 만든다).
  - 이유: 쌓인 층이 적을수록 충돌이 적다. 어기면: 아침 병합에 충돌이 몰린다.
- 보류 기능을 사람이 squash로 병합한 뒤 그 위에 쌓인 기능 브랜치에는 단계 브랜치를 병합해 넣는다(rebase·강제 푸시 금지). 충돌은 `-X ours`로 풀고 바뀐 파일을 `git diff --stat`으로 확인한 뒤 일반 푸시한다.
  - 이유: 11/5 #9, #12 충돌을 이렇게 풀었다. 어기면: 강제 푸시 금지선을 넘는다.

## 배포

- 공개 주소에는 검사·시험을 통과한 최신 브랜치를 배포한다. 보류 PR이어도 된다. 지정한 Vercel 프로젝트에만 배포한다.
  - 이유: 아침 시연이 끝까지 되어야 한다. 어기면: 보류 기능을 시연에서 못 본다.
- 배포한 브랜치와 커밋을 `morning-report.md`에 적는다.
  - 이유: 공개 주소의 코드가 main과 다를 수 있다. 어기면: 시연한 코드와 병합할 코드를 헷갈린다.
