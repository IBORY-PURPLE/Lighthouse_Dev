# 08 화면 정의

근거 표기는 `apps/web/` 기준 `파일:줄`이다. 낭독 문구는 `src/lib/speech.ts`의 `STATUS`와 컴포넌트 원문이다. 화면 시험(Playwright)은 가짜 음성 입력 기준이다(tests/e2e/helpers/fakeSpeech.ts:28). 실제 아이폰, VoiceOver, 실제 음성 인식 동작은 AI가 확인하지 못했다. 아래 "낭독"은 낭독 영역에 들어가는 글자이며, VoiceOver가 실제로 읽는지는 확인 전이다.

## 0. 공통

- 문서 언어 `ko`, 뷰포트 `device-width`(layout.tsx:12-15, 19).
- 낭독 영역은 `<p role="status">` 하나이고 비어 있어도 항상 그린다(StatusRegion.tsx:2-8). 화면마다 하나만 둔다(volunteer/page.tsx:64-67).
- 화면 제목(h1)은 `tabIndex=-1`이고 열릴 때 초점을 받는다(page.tsx:22-24, volunteer/page.tsx:52-56).
- 주소로 열리는 페이지 세 곳 `/`, `/volunteer`, `/speech-probe/`는 접근 쿠키 없이도 열린다. `src/`에 접근을 막는 미들웨어가 없고, 공개 주소 시험이 쿠키 없는 첫 화면과 음성 시험 페이지의 200을 확인한다(tests/e2e/public.spec.ts:26-31). 접근 코드는 서버 함수 호출 때 확인한다(아래 4절).
- 입력 방식 기본값은 음성이다(`PRIMARY_INPUT = "speech"`, speech.ts:6). 브라우저에 음성 인식이 없으면 입력창으로 간다(SpeechInput.tsx:63-66).

## 2. 봉사자 화면 `/volunteer` (시연)

- 목적: 이용자 요청을 보고, 음성이나 입력으로 질문해 AI의 "찾는 방법"을 받는다.
- 문서 제목: "시연: 봉사자 화면 - LightHouse"(volunteer/layout.tsx:3-5). 제목(h1): "봉사자 화면(시연)"(volunteer/page.tsx:71-73).

### 상태별 낭독 문구

입력 부품의 음성·입력창 단계(듣는 중, 못 들음, 인식 불가)는 이용자 화면과 같다. 다른 것만 적는다.

| 상태 | 낭독 영역 | 초점 | 근거 |
|---|---|---|---|
| 도착, 매칭 있음 | 시연: 봉사자 화면으로 바뀌었습니다. 이용자 요청: {요청}. (열린 뒤 100ms 지나 채운다) | h1 | volunteer/page.tsx:25-29, 58-63 |
| 도착, 매칭 없음 | 매칭 정보가 없습니다. | h1 | volunteer/page.tsx:63, tests/e2e/match.spec.ts:299-303 |
| 입력창에서 빈 채로 제출 | 입력창에 질문을 입력하세요. | 입력창 | speech.ts:32 |
| 질문 제출 | 답변을 만들고 있습니다. 이전 답변은 지운다 | 유지 | speech.ts:33, VolunteerChat.tsx:41-42 |
| 답변 수신 중 | 낭독 영역은 그대로. 글자는 답변 영역에 이어 붙는다 | 유지 | VolunteerChat.tsx:48-50, 79 |
| 답변 도착 | 답변이 도착했습니다. | 답변 영역 | speech.ts:34, VolunteerChat.tsx:36-38, 54-57 |

- 낭독 영역은 화면에 하나다. 입력을 건드리기 전에는 도착 안내를, 건드린 뒤에는 입력 부품의 문구를 보인다(volunteer/page.tsx:64-67).
- 답변은 "검색어", "확인할 조건", "찾는 순서" 세 항목을 쓰라고 지시문이 요구한다(prompt.ts:12-15). 실제 답이 지키는지는 챗봇 고정 질문 시험과 공개 주소 완주 시험이 본다(.claude/rules/chatbot-quality.md, tests/e2e/public.spec.ts:117-120). 지시문만으로 형식이 늘 지켜지지는 않는다. 커밋 870c13c의 공개 주소 시험에서 답이 "1. 검색어:"처럼 번호를 붙여 와 위반으로 실패했다. 답이 길어 잘리면 끝에 "답변이 길어 일부가 잘렸습니다."가 붙는다(llm.ts:11, 86).
- 대화 기록은 이어지지 않는다. 질문마다 답변 영역이 새로 채워진다(VolunteerChat.tsx:42, llm.ts:66-69).

## 3. 음성 시험 페이지 `/speech-probe/`

- 목적: 아이폰에서 브라우저 음성 인식이 되는지 보는 정적 시험 페이지. 앱 화면과 이어지지 않는다. 제목 "LightHouse 음성 시험"(public/speech-probe/index.html:6).
- 주소 `/speech-probe`는 `index.html`로 다시 쓴다(next.config.ts:4-8).
- 요소: h1 "음성 인식 시험", 버튼 "즉시 시작", 버튼 "1초 뒤 시작", 결과 영역(초점을 받는다), `role="status"` `aria-live="assertive"` 낭독 영역, 접힌 "상세 이벤트 로그"(index.html:98-112, 133-137).
- 낭독 문구: 시작 시 "준비됐습니다. 즉시 시작 또는 1초 뒤 시작을 누르세요."(238), 인식 API가 없으면 "음성 인식을 쓸 수 없습니다. 입력창 받아쓰기로 가면 됩니다."(147), 듣는 중 "듣고 있습니다. 말씀하세요."(158), 결과 "이렇게 들었습니다: …"(197).
- 페이지 안내문에 "아무것도 서버로 보내지 않습니다"(index.html:99)라고 있고, 스크립트에 `fetch` 호출이 없다.
- 이 페이지 결과는 사람이 아이폰으로 본다. AI가 실제 인식을 확인한 것은 아니다.

## 4. 접근 코드가 없을 때

- 페이지는 열린다. 막히는 곳은 서버 함수다: `/api/match`와 `/api/chat`이 401을 돌려주고, 화면은 "접근 코드가 필요합니다. 시연 주소로 다시 열어 주세요."를 낭독 영역에 넣는다(match/route.ts:39-41, chat/route.ts:100-102, speech.ts:29).
- 쿠키 발급은 `GET /enter?code=`로만 되고, 틀린 코드면 평문 401 "접근 코드가 올바르지 않습니다."를 받는다(enter/route.ts:17-28).
- 코드 값과 시연 주소는 이 문서에 적지 않는다.

## 5. 아직 없음

- 이용자 화면에 봉사자 응답, 진행 상황, 알림 화면은 없다. 연결 뒤에는 시연용 버튼만 있다(page.tsx:52-54).
- 봉사자가 이용자 요청을 직접 고르거나 받는 화면은 없다. `/volunteer`는 같은 탭 `sessionStorage`의 값을 읽는다. 다른 기기에서 열면 "매칭 정보가 없습니다."가 된다(volunteer/page.tsx:36-41, matchHandoff.ts:78-84).
